# 描画テストの WebView をウィンドウに入れる

## ステータス

承認

## コンテキスト

`ConversationRenderingTests` の `rendersEveryFormulaInMaterial()` が、数式を263個含む教材を描くときに待ち時間を超えて失敗することがあった。
テストの `RenderingHarness` は、WebView を作るだけでウィンドウに入れていなかった。

Apple の [`WKPreferences.inactiveSchedulingPolicy`](https://developer.apple.com/documentation/webkit/wkpreferences/inactiveschedulingpolicy-swift.property)（iOS 17 以降）は、
ウィンドウに無い WebView の扱いを決める設定で、既定値は `.suspend`（タスクを完全に止める）である。

同じ教材を描くのにかかった時間は次のとおり（すべて Simulator の iPhone 17、iOS 26.5）。

| 実行環境 | Simulator の状態 | 描画が終わるまで |
|---|---|---|
| テスト（ウィンドウなし） | 起動済み・負荷なし | 1.2〜1.3秒 |
| テスト（ウィンドウなし） | 起動直後 | 22〜41秒 |
| テスト（ウィンドウなし） | 起動済み・8コアを占有 | 58.7秒 |
| テスト（ウィンドウあり） | 起動済み・8コアを占有 | 2.5秒 |
| アプリ | 起動済み | 0.5〜0.6秒 |
| アプリ | 起動済み・8コアを占有 | 0.46秒 |

時間はテストではテストの開始から、アプリでは JavaScript の開始から数えた。
遅いのはウィンドウに入れていないテストだけで、`WebRenderer` の処理やアプリの動きに問題は無い。

## 決定

`RenderingHarness` で、テスト用の `UIWindow`（375×812）を作って WebView を入れ、`isHidden = false` にする。
変更するのはテストだけで、本番のコードは変えない。

実際のアプリでも WebView はウィンドウの中で動くため、テストの条件をそれに揃える。

## 検討した他の案

- **待ち時間を延ばす**：テストが実際のアプリと違う条件のまま残り、かかる時間も他に動いている処理に左右され続ける
- **`inactiveSchedulingPolicy` を `.none` にする**：WebView を作る本番のコードに手を入れるか、作った後で設定を変える必要がある。効果は試していない
- **アプリ本体にテストのターゲットを作る**：テストをパッケージ側に置く今の構成と合わなくなる。効果は試していない

## 結果（受け入れたコストを含む）

- ウィンドウに入れた後、Simulator の起動直後や負荷が高い状態を含めて、描画テストのスイートは9回続けて通った。待ち時間30秒・1つずつ実行の設定で測った
- ウィンドウに入れても、待ち時間10秒・並列実行の設定では、Simulator の起動直後に5回中1回、スイートの全テストが待ち時間を超えて失敗した。待ち時間と実行順の設定はこの決定では変えない
- ウィンドウなしで処理が完全には止まらず遅く進んだ理由と、公式の説明と測定で見えたプロセスの優先度の対応は確かめていない。実機でも測っていない
