# アーキテクチャに The Composable Architecture（TCA）を採用する

## ステータス

提案

## コンテキスト

- 段階2の受講では、講義本文と質問応答を NDJSON のストリーミングで受け取る（`shared/api.ts` の `LectureStreamLine`）
- 受信の途中で画面を離れる・別の講義に切り替えるといった操作があり、受信中の処理のキャンセルと、
  遅れて届いたデータの扱いを決めておく必要がある

## 決定

- アーキテクチャに TCA を採用する
- バージョンは 1.26.2 に固定する（Exact）

ストリーミングの状態遷移・途中キャンセル・遅れて届いたデータの扱いを、
仕組みとして持てるため（`Docs/REQUIREMENTS.md` §7）。

## 検討した他の案

### MVVM

- 利点：
  - 学習を修了しており、理解が深い
  - このアプリの規模で1人で開発するなら、MVVM で十分という判断も成り立つ
- 採らなかった理由：
  - MVVM の学習で、次の弱点に気付いた。途中の状態をテストするにはタイミングの制御が必要で難しい。
    また、連続して検索すると応答が競合する。受講のストリーミングで扱う途中キャンセルと、
    遅れて届いたデータの無視は、これと同じ種類の問題になる
  - MVVM は規約なので、違反を検知できない。実装を AI に任せる以上、規約ではなく構造で守れる方が、
    レビューで逸脱を見つけやすい
- 比較の根拠：小規模なアプリで MVVM と TCA の両方を試した経験と、AI講師の要件の分析。
  AI講師そのものを両方の方式で実装して比べてはいない

## 結果（受け入れたコストを含む）

- 外部ライブラリは TCA だけに限る（`CLAUDE.md`）
- TCA のバージョンを上げるときは、ユーザーが判断する
