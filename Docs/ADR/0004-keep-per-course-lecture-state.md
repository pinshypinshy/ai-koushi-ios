# 講義ごとに受講の状態を持ち、講義を切り替えても受信を続ける

## ステータス

承認

## コンテキスト

- 講義本文・質問応答の受信中や、ステップの完了を待つ間に、利用者がサイドバーで別の講義を選ぶことがある。
  そのとき、元の講義の受信をどう扱うかを決める必要がある
- 受信をやめて通信を切った場合、サーバー（Cloudflare Workers）が生成を続けるかは保証されない。
  公式ドキュメントは、相手が切断した後の処理を「may be canceled」としている。Web版のサーバーは、生成を
  `ctx.waitUntil()` に渡していない
- 生成が続いていて、生成が終わる前に元の講義へ戻ると、そのステップにはまだ発言が無い。講義本文を自動で呼ぶ条件
  （`Docs/REQUIREMENTS.md` §4.7）を満たすため、同じステップの応答を2つ生成しうる。料金が2回かかり、本文が2つ並ぶ
- 切り替えたときに受講の状態を捨てると、失敗の表示や「自動では1回」の記録も消える。戻ったときに、
  本文もボタンも無い画面になる場合がある

## 決定

- 別の講義を選んでも、受信とステップの完了の待機を続ける。届いた文字や結果はその講義にだけ反映し、
  戻るとその続きや結果を表示する
- `CourseFeature` モジュールに、選択中の講義を決める `CourseFeature` と、講義1つ分の受講を扱う
  `LectureFeature` を置く。`CourseFeature` は、開いた講義ごとの `LectureFeature` の状態を一覧で持ち
  （TCA の `forEach`）、選択中の講義の分だけを画面に出す。モジュールは増やさない
- 講義ごとの状態は、ログアウトするまで残す。サイドバーの取り直しで一覧から消えた講義は、その状態を捨て、
  受信もやめる。ログアウトとセッション切れでは、すべての受信をやめる
- 受信中・ステップの完了を待つ間・失敗の後の読み直しの間の講義を選び直しても、講義を取得しない
  （取得した内容で、受信中の発言や待っている結果を上書きしないため）

## 検討した他の案

### Reducer を1つにし、講義を切り替えたら受信を止めて状態を初期化する

- 採らなかった理由：受信の停止と、受信中の文字・エラー・入力欄などの初期化を、項目ごとに手で書くことになる。
  書き忘れると前の講義の文字が別の講義に出るが、型の検査でもテストでも見つけにくい

### 講義を切り替えたら、受講の状態を作り直す

`CourseFeature` を丸ごと作り直す案と、同じモジュールの子の `LectureFeature` だけを作り直す案を検討した。

- 利点：作り直すことがそのまま片付けになり、書き忘れが起きない
- 採らなかった理由：作り直すと受信をやめることになり、上のコンテキストのとおり、戻ったときに同じ応答を
  二重に生成しうる。失敗の表示も消える

### 受講を新しいモジュールに分ける

- 採らなかった理由：使うのは講義画面だけで、コンパイラに禁じさせたい依存も無い（ADR 0002 の分け方の基準に当たらない）。
  別モジュールの Feature にすると `AppFeature` で組み合わせることになり、講義画面の振る舞いが `MainFeature` に漏れる

## 結果（受け入れたコストを含む）

- 受信をやめないので、サーバーが切断で生成を止めるかどうかに左右されない。途中まで生成した分の料金も無駄にならない
- 失敗の表示を講義ごとに残すので、戻ったときに本文もボタンも無い画面にならない
- `Docs/REQUIREMENTS.md` §4.10 を、受信をやめる形から続ける形に変えた
- 講義1つ分ではなく、開いた講義ごとの状態を一覧で持つため、作りが複雑になる
- 講義の取得（§4.6）に、受信中などの講義を選び直しても取得しない条件が要る
- `LectureFeature` から `MainFeature` への知らせ（セッション切れ、利用状況の取り直し）は、`CourseFeature` を経て2段で中継する
