# Markdown と数式を表示する WebView を、共通の器とページに分ける

## ステータス

承認

## コンテキスト

- 確認テストの問題文・選択肢・解説も、講義の会話と同じく WebView で表示する（ADR 0007）
- これまでの WebView の部品は会話だけを前提に作っており、WebView の世話（読み込み・準備完了の待機・命令の送信・知らせの受信・エラーの報告・処理が落ちたときの読み直し）が会話専用の型と結び付いている
- 今後の機能の拡張で、Markdown と数式を表示する画面がさらに増えうる

## 決定

- モジュール `ConversationWebView` を `MarkdownWebView` に改名する
- モジュールの中を、共通の器（Swift の `Core/`、TypeScript の `core/`）と、ページごとの中身（`Conversation/`・`Quiz/` と `conversation/`・`quiz/`）に分ける
- 共通の器を、ページが従うひな形にする。ページごとに書くのは、Swift では送る命令の型と受け取る知らせの型、TypeScript では命令の形の検査と描画だけにする。書き忘れや型の誤りはビルドで止まるようにする
- JavaScript からの知らせは、どのページからも届くもの（準備完了・エラー・枠に触れた）と、ページ固有のものに分ける
- ページを表示する View の名前は「<ページ名>WebView」にそろえる（`ConversationWebView`・`QuizWebView`）
- 確認テストを作る前に、振る舞いを変えずに、既存の会話の部品をこの形に作り直す

## 検討した他の案

### 既存の部品の共通部分だけを切り出し、確認テストを足す（改名しない）

- 採らなかった理由：今後ページを足すたびに同じ判断が要る。名前と中身が合わない

### 1枚のページで会話と確認テストを切り替える

- 採らなかった理由：1つのページに2つの描き方と2種類の命令が混ざる

### 汎用の部品（段落・ボタンなど）を描くページにする

- 採らなかった理由：選択状態や正誤の印まで汎用の部品で表すのは過剰

### 共通の器を別のモジュールにし、ページごとにモジュールを分ける

- 採らなかった理由：同梱物はモジュールごとに分かれ、WebView が読める範囲は1つのフォルダに限られる。フォントを共有するには、確認テスト専用の JavaScript も共通のモジュールに置くことになる

## 結果（受け入れたコストを含む）

- ページを足すときは、`Conversation/`・`conversation/` にあたるフォルダを1組作るだけで済む。共通の器には手を入れない
- 確認テストの前に、改名・Swift の作り直し・TypeScript の作り直しの3回の作業が入る
- 同じモジュールなので、ページ同士が互いの型を使うことはコンパイラでは防げない
- Swift と TypeScript の間（JSON）の食い違いは、これまでどおり実行時の形の検査で見つける
